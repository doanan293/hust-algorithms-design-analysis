\section{Proposed Algorithm}
\label{sec:method}

This section presents the proposed sample-scored block search, which we denote SBS, and its schedule-repair variant SBS-R. Both methods take a scenario as input and output a plan $(q,\pi,w)$: a trajectory, a path $\pi_a$ for every alert (or none), and bandwidth weights. The candidate set of \cref{sec:model} only provides the initial plan; during the search, paths are generated from the current plan and may leave the candidate set. \Cref{fig:pipeline} summarizes the pipeline. We first explain why the blocks are not solved as convex subproblems, then introduce the two ingredients shared by all blocks, namely the weighted bandwidth rule and the design scorer, and finally describe the blocks of SBS, the repair loop of SBS-R, and a leximin variant used to isolate the effect of the objective.

\subsection{Design Rationale}
\label{sec:algorithm}

We keep the three-block structure of~\cite{huang2025ddatsap} but do not solve each block as a convex problem, a choice motivated by three preliminary tests on six evaluation scenarios with ten realizations each. When the bandwidths of the solution of Problem (P2) were used as a static schedule, the timely-delivery ratio fell from \num{0.410} for the fixed-trajectory baseline FixedTour to \num{0.128}; used as bandwidth-sharing weights, they reached \num{0.404}, and paths taken from the solution of (P2) reached \num{0.412}. Guidance from the LP therefore does not carry over to the EDF scheduler, and under the PrLoS channel the trajectory block admits no valid convex surrogate for an objective that counts alerts. Search scored by the evaluator itself, by contrast, raised the ratio to \num{0.427} when scoring on expected rates and to \num{0.449} when scoring on five sampled realizations, while scoring on expected rates even lowered one scenario from \num{0.372} to \num{0.305}. We therefore implement each block as an evaluated local search: the block generates neighbors of the current plan by changing a small part of it, scores each neighbor, and keeps it only if the score improves. Compared with a surrogate-based decomposition, this design measures every accepted change on the exact objective and scheduler used for evaluation, and it requires only samples of the channel rather than a convex surrogate of it.

\subsection{Plan Representation and Design Scoring}
\label{sec:weights}

A plan carries a weight $w_{e,n}\ge 0$ for every radio link $e$ and slot $n$ instead of an explicit bandwidth schedule. In each phase of a slot, let $\mathcal B_n$ be the set of access links with queued data, or the set of at most two downlinks whose queue heads have the earliest deadlines. As illustrated in \cref{fig:slot}, the bandwidth allocated to a link $e\in\mathcal B_n$ is
\begin{equation}
\label{eq:weights}
b_{e,n}=B_{\mathrm{tot}}\frac{w_{e,n}}{\sum_{e'\in\mathcal B_n}w_{e',n}},
\end{equation}
\noindent with equal sharing when the weights sum to $0$. The equal-sharing rule of the baselines is the special case in which all weights equal $1$. The weights are fixed before the mission, whereas the actual bandwidth depends only on the current queues, so the policy uses no future information. Unlike a static bandwidth schedule, which falls out of step with how the EDF scheduler serves the queues, this rule follows the backlog in every slot while still letting the search shift spectrum toward specific links.

\label{sec:scoring}
The search never uses the evaluation realizations. It scores a plan on $M_d=5$ design realizations, drawn from a random stream distinct from the evaluation stream, by summing the lexicographic key \eqref{eq:objective} over these realizations. Each scoring call counts as one evaluation, and the total number of evaluations is capped by a budget $E=2000$; when the budget is exhausted, the method returns the best plan found so far. A change is accepted only if the key increases strictly, so the key of the current plan never decreases. During design scoring, the independent ledger checker is skipped and $\mathrm{Conn}$ is cached per trajectory and realization, since neither affects the search decisions; this leaves the returned plan unchanged and speeds up the search by a factor of about \num{2.9}. The final evaluation on the evaluation realizations still runs the checker.

The true objective is the expectation of the lexicographic key over the channel distribution. Summing the key over $M_d$ design realizations is a sample average approximation (SAA) of this expectation with sample size $M_d=5$, whereas scoring on expected rates corresponds to the deterministic equivalent problem. Because design and evaluation realizations come from different random streams, all reported timely-delivery ratios are out-of-sample estimates. Our experiments on the number of design realizations examine the sample size of this SAA.

\subsection{Block Search}
\label{sec:b2}
SBS starts from the plan of FixedTour with all weights equal to $1$ and performs at most ten rounds of three blocks. Each block changes one part of the current plan while the other two are held fixed, and every change is scored and accepted only if the key increases strictly. The path and trajectory blocks begin with one ledger evaluation of the current plan on the design realizations, which records, for every link and slot, the transmitted bits and whether the link carried its full capacity. These records make the neighbors depend on the current trajectory and bandwidth: a path is rerouted around the links that the current plan congests, and the trajectory is moved toward the radio links that are short of capacity. All random choices use one generator seeded by the scenario, so a run is reproducible.

\paragraph{Path block.} The block visits the alerts in a random order drawn without replacement with probability proportional to $1/(d_a-r_a)$, so urgent alerts tend to come first while successive rounds explore different orders; with a limited budget, this order spends evaluations first where a deadline is most at risk. For alert $a$ with current path $\pi_a$, the block tries the following neighbors in turn, illustrated in \cref{fig:moves}(a).
\begin{itemize}
\item \emph{Kind switch:} the same drop node with the other kind of first hop, i.e., a ground path becomes a UAV path and vice versa. A ground path is generated only if the source is within ground range of the node, and only for sources that reach some relay over the ground at all, so a source isolated from the ground network keeps UAV paths only.
\item \emph{Entry switch:} the same kind of path through another entry node $v$, followed by its minimum-hop backhaul route. Each reachable node receives an estimated completion time
\begin{equation}
\label{eq:entry-time}
T_a(v)=T^{\mathrm{acc}}_a(v)+\sum_{e\in\mathrm{route}(v)}\Bigl(\frac{L_a}{\hat C_e}+\Delta\Bigr),
\end{equation}
\noindent where $\hat C_e$ is the capacity of backhaul edge $e$ minus the rate it carries in the current plan during $[r_a,d_a)$, averaged over the design realizations and floored at $C_e/1000$, and $T^{\mathrm{acc}}_a(v)$ is the ground transmission time of $L_a$ for a ground path or the mean distance from the UAV's current positions in $[r_a,d_a)$ to $v$ divided by $V_{\max}$ for a UAV path. The block draws $M_e=3$ entry nodes without replacement with probability proportional to $1/T_a(v)$ and tries them in increasing $T_a(v)$, which favors nearby relays with spare backhaul without excluding the others.
\item \emph{Backhaul detour:} the backhaul edge $(u,v)$ of $\pi_a$ that the current plan congests in the most slots of $[r_a,d_a)$ is removed, and the path is continued from $u$ by a minimum-hop route to $c$ that avoids $(u,v)$ and the nodes of $\pi_a$ before $u$. The part of $\pi_a$ up to $u$ is kept. No detour is generated when $\pi_a$ crosses no congested edge or when no such route exists.
\item \emph{Skip:} the alert is left unserved, which frees capacity for the others.
\end{itemize}
An alert that is currently unserved tries its candidate paths instead. Every generated path is a loop-free route from $s_a$ to $c$ over surviving edges, so the neighborhood stays within the feasible set while reaching paths that are not in the candidate set.

\paragraph{Bandwidth block.} The block visits the radio links in use in decreasing order of the total size of the alerts they carry and tries to multiply all weights of a link by $2$, or by $1/2$ if doubling is rejected. A radio link that enters the plan through a new path starts with weight $1$.

\paragraph{Trajectory block.} The block moves a segment $q[i],\dots,q[j]$ of the current trajectory, $1\le i\le j\le N-1$, by a common displacement $\lambda u$ with a unit direction $u$, as illustrated in \cref{fig:moves}(b). The steps inside the segment are unchanged, so constraint \eqref{eq:mobility} only restricts the two boundary steps, and the largest feasible displacement is
\begin{equation}
\label{eq:shift}
\lambda^\star=\max\bigl\{\lambda\ge 0:\ \norm{q[i]+\lambda u-q[i-1]}\le V_{\max}\Delta,\ \norm{q[j]+\lambda u-q[j+1]}\le V_{\max}\Delta\bigr\},
\end{equation}
\noindent obtained in closed form from two quadratic inequalities. When $\lambda^\star=0$ because a boundary lies on a segment flown at full speed, the segment is widened by one slot on each side, at most ten times. The segments come from the ledger evaluation: for every radio link between the UAV and a ground point $k$, the priority of slot $n$ is the number of design realizations in which the link is saturated at $n$, multiplied by $\sum_a L_a/(d_a-r_a)$ over the alerts on the link whose window contains $n$. Consecutive slots with positive priority form a segment, $u$ points from the centroid of the segment toward $k$, and the block draws $W=5$ segments with probability proportional to their total priority. Each drawn segment is tried with $\lambda=\lambda^\star$ and then with $\lambda^\star/2$. In the example of \cref{fig:moves}(b), the UAV hovers between two sources whose uplinks share the access band; if the alert of $s_1$ is larger or more urgent, its uplink accumulates more priority and the segment is pulled toward $s_1$. To keep moves that change the zone order available, the block also tries, with probability $0.1$ per round, one tour drawn uniformly from a family of up to $90$ feasible tours, which visit an ordered subset of the damage zones in straight lines at speed $V_{\max}$, hover at the zone centers or the centroids of their sources, and split the remaining time among the stops equally, in proportion to the number of alerts of each zone, or in proportion to $\sum_a 1/(d_a-r_a)$ over the zone. Every trajectory produced by the block satisfies \eqref{eq:mobility} by construction.

The search stops when a round accepts no change or the budget is spent. Compared with SCA-based trajectory design, the trajectory block gives up the gradient of a convex surrogate, but every move it makes is feasible and evaluated on the exact objective; compared with scanning a fixed family of tours, the moves follow the incumbent and the current congestion of the plan, which lets the UAV settle at positions that no predefined tour contains.

\subsection{Schedule Repair}
\label{sec:repair}
The blocks of SBS change one decision at a time without regard to which alerts are about to miss their deadlines. SBS-R targets these alerts directly by adding a repair loop after the trajectory block of every round, as illustrated in \cref{fig:repair}. A ledger evaluation of the current plan records, for each alert and design realization, its slack $d_a-1-t_a$, where $t_a$ is the completion slot and the slack is set to $-1$ for late alerts, together with the hop that holds the alert's data for the most slots and the links whose capacity is exhausted. The risk of an alert is the fraction of design realizations in which it is late or has a slack of at most $\theta=2$ slots, and the loop considers at most $R=10$ alerts with the highest risk. If the bottleneck hop of such an alert is a radio link, Operator~1 doubles its weight within the slots $[r_a,d_a)$ only, which moves bandwidth from the other links of the same phase to this alert. Operator~2 generates the neighbors of the alert's path as in the path block, ranks them first by the number of congested links in the alert's window and then by estimated cost, and accepts the first one that increases the key. All operators share the budget with the three blocks, so SBS-R and SBS have the same maximum number of evaluations. The mechanism follows the destroy-and-repair principle of large neighborhood search~\cite{ropke2006alns}.

\subsection{Overall Algorithm and Complexity}
\label{sec:overall}

\Cref{alg:bcd-repair} summarizes the method; SBS is obtained with repair disabled and SBS-R with repair enabled.

\begin{algorithm}[htbp]
\caption{Sample-scored block search with schedule repair.}
\label{alg:bcd-repair}
\begin{algorithmic}[1]
\Require Scenario, candidate set, design realizations, budget $E$, maximum rounds $I_{\max}=10$, seed
\Ensure Trajectory $q$, paths $\pi$, bandwidth weights $w$
\State $(q,\pi)\gets$ plan of FixedTour; $w\gets 1$; $\kappa\gets$ key of $(q,\pi,w)$
\For{$i=1,\dots,I_{\max}$}
    \State Path block: ledger evaluation; for each alert in urgency-weighted random order, try its kind switch, $M_e$ entry switches drawn by $1/T_a(v)$, the detour around its most congested backhaul edge, and skipping it
    \State Bandwidth block: for each link in use, try $w_e\gets 2w_e$, then $w_e\gets w_e/2$
    \State Trajectory block: ledger evaluation; draw $W$ segments by priority and try each shift with $\lambda^\star$, then $\lambda^\star/2$; with probability $0.1$ try one tour of the feasible tour family
    \If{repair is enabled}
        \State Ledger evaluation; select at most $R$ alerts with the highest deadline risk
        \ForAll{at-risk alerts $a$}
            \State Operator 1: double the weight of the bottleneck hop within $[r_a,d_a)$
            \State Operator 2: try neighbor paths by number of congested links, then by cost
        \EndFor
    \EndIf
    \State Accept each trial iff the key increases strictly; stop as soon as the budget $E$ is spent
    \If{no change was accepted in this round} \textbf{break} \EndIf
\EndFor
\State \Return $(q,\pi,w)$
\end{algorithmic}
\end{algorithm}

One round uses at most $1+(M_e+3)\abs{A}$ evaluations for the path block, $2\abs{\mathcal L_{\mathrm{used}}}$ for the bandwidth block, and $2+2W$ for the trajectory block, plus $1+R(M_e+3)$ for the repair loop of SBS-R, where $\mathcal L_{\mathrm{used}}$ is the set of radio links in use. Generating the neighbors of one alert takes $O\bigl(\abs{V}(\abs{V}+\abs{E})\bigr)$ time for the routes, and drawing the segments takes $O(N\abs{\mathcal L_{\mathrm{used}}}\abs{A})$, both negligible next to an evaluation. Each evaluation costs $O\bigl(M_dN(\abs{\mathcal L}+\abs{A}\log\abs{A})\bigr)$, and risk detection scans the ledger in $O\bigl(M_d(N\abs{\mathcal L}+T)\bigr)$, where $T$ is the number of transmission records. The budget caps the total number of evaluations, so the planning time of SBS, SBS-Lex, and SBS-R is $O\bigl(EM_dN(\abs{\mathcal L}+\abs{A}\log\abs{A})\bigr)$, independent of the actual number of rounds. The method only guarantees that the key of the plan does not decrease; it does not guarantee optimality. The LP bound (P2), solved on the trajectory chosen by each method, measures the remaining room for improvement within the candidate set; since SBS may route alerts outside this set, its value on a realization can exceed the bound.

\label{sec:variants}
To separate the effect of the objective from that of the search, SBS-Lex runs the same search as SBS with a different key. Let $\bar f_a$ be the fraction of the bits of $a$ that reach the center before the deadline, averaged over the design realizations. The average delivery rate of $a$ divided by its required rate $L_a/((d_a-r_a)\Delta)$ equals exactly $\bar f_a$, so $\min_a \bar f_a$ is a normalized version of the max--min objective of~\cite{huang2025ddatsap}. Because a single undeliverable alert forces $\min_a\bar f_a=0$ for every plan, SBS-Lex compares plans in leximin order:
\begin{equation}
\label{eq:leximin}
\bigl(\bar f_{(1)},\bar f_{(2)},\dots,\bar f_{(\abs{A})},\ \textstyle\sum_{\omega}\sum_a z_{a,\omega},\ \mathrm{Conn}\bigr),\qquad \bar f_{(1)}\le\bar f_{(2)}\le\dots\le\bar f_{(\abs{A})},
\end{equation}
\noindent where an unserved alert has $\bar f_a=0$. The difference between SBS and SBS-Lex measures the cost of optimizing fairness instead of the number of timely alerts.
